Help Pulse

A small, reproducible pipeline that turns “not helpful” votes and free-text comments into a prioritized backlog. Public demo. Mock data only.

What it isTriage rules plus a static dashboard
StackPython · one HTML file · no npm
DataFictional feedback, IDs, and Help URLs
Role of AIDrafts a pass; a person reviews before anything is acted on

The problem

Help sites collect a steady stream of unhelpful votes and comments. Without a shared system, writers either read every record one by one in a CRM, or they triage inconsistently — the same bug three times, a broken link sitting next to a vague rant.

“Pulse” here is a health check on the docs: volume plus severity of feedback. It is not a product brand.

What the system answers

  • Should we act? Actionable / Non-actionable / Needs-info
  • What kind of fix? Broken link · incorrect info · missing info · unclear · route elsewhere
  • How urgent? P0–P3. P0 is always human-confirmed.

Two parts

The skill is the brain: written rules for triage, buckets, priority, and source validation. The dashboard is the face: heatmap, Fix First list, duplicate clusters, article drawer, work-item template.

This public repo is a sanitized, runnable demo of that idea — same architecture and UI patterns, mock data only.

How a pass is made

Open records only. Each row gets a provisional bucket, then — for the four content buckets — a check against the article itself. A claim the page bears out is Actionable. A claim the live article contradicts is Non-actionable. If the page will not load, the call stays flagged as source-unverified. “Route elsewhere” skips the article check; reading the doc cannot prove product behavior.

Priority walks a decision tree. Internal reporters can floor an actionable item at P1. A P3 that clusters to ten or more records steps up to P2. P0 — security, customer-data exposure, legal risk in the doc — never lands in the file without an explicit yes from a person.

AI drafts. A person approves. No auto-close, no auto-created work items, no publish.

Rules that stay hard

  • Doc-versus-product is a hypothesis, not a verdict. Routing to product means “confirm with someone who knows,” not “the product is broken.”
  • Triage on signal, not tone. Profanity does not change the call. The note is restated professionally; the customer’s words stay in the source column.
  • No validity verdict without retrieved content. If the article did not render, do not invent what it says.
  • One work item per cluster, not per vote. Every member record stays visible on the dashboard.

What is in the demo

Forty-four mock records map to nine stub Help articles baked into a single index.html. Heatmap, filters, clusters, drawer, and the work-item template all run locally. Feedback links go to example.com. The live Help host is fiction. The feedback form is off on purpose.

IDs look like HTAV-1000001. Help URLs stay on help.example.com. A verify script fails the build if a real host or a live ID slips in.
