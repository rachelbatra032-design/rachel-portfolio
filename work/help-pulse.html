Help Pulse

Triage for Help and Training Article Votes on Salesforce Revenue Cloud. Written rules, a shared dashboard, and a public demo that runs on mock data only.

RoleWrote the triage rules and built the dashboard
Inside SalesforceShipped. About 200 people use it. Processing time down about 70 percent. Six to eight weeks of writer time back each release.
Public demoSame shape. Forty-four fictional records. No live customer text.
StackPython, one HTML file, no npm

01. The pile

Revenue Cloud help articles collect unhelpful votes and free-text comments. Each one is an HTAV: a Help and Training Article Vote. Before this, a writer opened the CRM and read them in order. The same broken See Also link showed up three times. A rant with no locatable ask sat next to a wrong percentage. Nothing told you what to do first.

Help Pulse is the name on the public demo. At work it is the HTAV pass: a monthly export, a set of written calls, then a dashboard the team can share instead of a private spreadsheet.

02. The three questions

Every open record has to answer three things, in this order.

  • Should we act? Actionable, non-actionable, or needs more information.
  • What kind of fix? Broken link, incorrect info, missing info, unclear, or route it elsewhere.
  • How urgent, if we act? P0 to P3. P0 never writes itself.

The buckets came down to five. Confusing and vague folded into unclear. Product bugs, support how-tos, and “please make this a PDF” all route elsewhere. Reading the article cannot prove that the product is broken.

03. How a pass actually runs

Closed records stay out. Each open row gets a provisional bucket from the feedback itself. Then, for the four content buckets, someone has to open the live article and check the claim. If the page says what the customer said it said, the row is actionable. If the page already contradicts it, the row is not. If the page will not load, the call stays flagged as unverified. Route-elsewhere skips that check on purpose.

Priority is a ladder, not a vibe. A wrong number that sends the reader the wrong way is P1. A missing value that blocks a setup is P2. Wording, order, tiny screenshots: P3. Internal reporters floor an actionable item at P1. If a P3 clusters to ten or more of the same issue, it steps to P2. Security, customer-data exposure, or legal risk in the doc is P0, and it does not land in the file until a person says yes in the chat.

The rules were settled on a labeled batch of 83 records so two people would make the same call the next month, instead of re-arguing each row.

AI drafts the pass. A person reviews it. Nothing auto-closes. Nothing files a work item on its own. Nothing publishes.

04. What the dashboard is for

The written rules are useless if the queue still lives in one person’s head. The dashboard is one HTML file: a heatmap of bucket against priority, a Fix First list, duplicate clusters, an article drawer, and a work-item template. One cluster is one work item. Every member vote stays visible so you can see the pile, not only the ticket.

Tone does not change the call. If the feedback names a real, fixable problem, it is actionable. The note is restated without the heat. The customer’s words stay in the source column.

05. What you can open

The public repo is a clean copy of that shape. Forty-four mock records map to nine stub articles baked into index.html. IDs look like HTAV-1000001. Help URLs stay on help.example.com. Feedback links go to example.com. A verify script fails the build if a real host or a live ID slips in. The feedback form is off on purpose.
